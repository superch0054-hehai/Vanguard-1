## 阶段 1：点灯（light，2.1.2）—— ✅ 2026-09-29 通过

**目的**：验证写链路能不能通，并排除两个此前未知的问题：
要不要先发 `connect` 登录；我们的报文帧（结尾少两个换行）写操作是否接受。

**前置状态**（执行前只读查询）：

```
27-188-10-6  finish 完成  reservepause=1
27-188-10-7  finish 完成  reservepause=1
27-188-10-8  finish 完成  reservepause=1
```

**执行**（每通道开灯一次、灭灯一次，共 6 次写操作）：

| 时间 | 命令 | 通道 | 设备回应 |
|---|---|---|---|
| 2026-09-29T20:32:57 | light（开） | 27-188-10-6 | `ok` |
| 2026-09-29T20:33:19 | light（关） | 27-188-10-6 | `ok` |
| 2026-09-29T20:33:19 | light（开） | 27-188-10-7 | `ok` |
| 2026-09-29T20:33:19 | light（关） | 27-188-10-7 | `ok` |
| 2026-09-29T20:33:20 | light（开） | 27-188-10-8 | `ok` |
| 2026-09-29T20:33:20 | light（关） | 27-188-10-8 | `ok` |

**结论**：

1. **写链路通**。设备接受我们的报文并回了协议规定的 `ok`。
2. **不需要 `connect` 登录** —— 我们的实现从不发登录，写操作直接成功。
3. **帧格式被写操作接受** —— 结尾只带 `#\r\n`（没有上游 aurora-neware 的
   `\n\n`），设备正常应答。这个差异可以放心放着。
4. `parse_ack()` 能正确读出回包的 `ok` 与通道四元组。
5. 通道与回应**一一对应**：给 10-7 发的命令，回应里就是 10-7 —— 没有串通道。

**总闸验证**（同日 20:33:20）：删除使能文件 `.control_enabled` 后再执行
`light 10-6`，被拒（退出码 2），拒绝理由完整，并记入审计日志
（`result: blocked`）。控制功能默认关闭，这一点是代码行为，不是口头约定。

**审计日志**：`~/batterylab/logs/control.log`，一行一条 JSON（时间/用户/命令/通道/回应）。
上面表格即由它导出。

## 故意不实现的命令（协议里有，我们不做）

| 命令 | 理由 |
|---|---|
| `broadcaststop` 2.1.8 | 整台设备一起停，误伤面最大；要停单通道用 `stop` |
| `goto` 2.1.11 | 跳过工步会在数据里留下永久缺口，不可逆 |
| `reset` 2.1.19 | 同样要工步文件，且会顶掉当前工步，收益为负 |
| `parallel` 2.1.15 | 需要多通道物理并联接线；协议里 `paralleltype` 取值表为空 |
| `chl_ctrl` 2.1.10 | 协议注明"IGBT通道模块控制，需要中位机和硬件支持"，BTS85 是否具备未知 |

这 5 条在 `control.py` 里被**注册为可见但拒绝**的子命令 —— 用户敲了会得到
明确的理由，而不是 argparse 的 invalid choice。每次拒绝都写审计日志。
