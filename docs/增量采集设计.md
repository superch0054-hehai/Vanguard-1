# 每日增量采集（live 区）—— 设计与使用

> 2026-09-30 实现。需求原话："一天能更新一次数据就行，不要等电池停下来才能读取数据"。
> 验收证据见文末。

## 一、解决什么问题

原设计里，采集器只在**看到测试结束**（working → finish/stop/protect）时才正式采集。
老化测试一跑几十天，期间 `data/` 里什么都没有。

现在采集器多了一个**每日节拍**：每天 02:00 对正在跑测试的通道做一轮**增量读取**，
把设备上新增的明细行追加到 `data/live/` 区 —— 不用等测试结束。

## 二、机制

```
collector（7×24 常驻，每 30 秒轮询一次状态）
   └─ 内部节拍：每天 02:00（--incremental-hour 可改）
        对每个 working 通道：
          ① inquiredf   → testid + 设备端数据点总数（如 263 → 5013）
          ② 与水位比（progress.json 里的 rows_collected）
          ③ 只 download 新增段（分块，单次 ≤ 1000 条）
          ④ 追加到 live detail.csv，更新水位
   失败 → 每 30 分钟重试，当天成功一次即停
   服务重启 → 启动时立即补拉一轮（重启期间错过的数据不丢）
```

三个底层命令都已**在跑着的测试上真机验证过**（2026-09-30，测试 263/264/265）。

## 三、数据放在哪

```
data/
  channel=.../testid=.../detail.csv   ← 正式数据集：结束时一次完整采集，一字不动
  live/
    channel=27-188-10-1/testid=263/
      detail.csv      ← 每日增量追加（列格式与正式 detail.csv 完全一致）
      progress.json   ← 水位 {"testid","rows_collected","total_on_device","updated_at"}
```

三条铁律：

1. **live 与正式数据集相互独立** —— 结束时仍做一次完整采集作为正式数据；
   口径、对账结果、SOH 报告全部只看正式数据集
2. **live 的列格式与正式 detail.csv 完全一致**（解析器/单位换算零改动可复用）
3. **watermark（水位）** 记"已拉到第几条"：不重复、不遗漏、可断点续传；
   `count < 水位` 说明数据异常，**拒绝拉取**（宁缺勿乱）

## 四、使用

| 操作 | 命令 |
|---|---|
| 手动跑一轮增量 | `python3 collector.py --incremental-now --data-dir ./data --channels 27-188-10-1,27-188-10-2,27-188-10-3` |
| 改节拍时间 | `--incremental-hour 8`（默认 2 点） |
| 关闭增量 | `--no-incremental` |
| 看进度 | 网页控制台首页「进行中的测试（每日增量）」，或看各目录的 `progress.json` |

## 五、边界情况（都已处理并有测试）

| 情况 | 行为 |
|---|---|
| 节拍失败（断连/设备忙） | 水位不动，每 30 分钟重试，当天成功即停 |
| 通道测试结束 | 跳过增量（正式采集接住），live 停在最后水位 |
| 通道被复用（testid 变了） | 水位清零，**另起新 testid 目录**，绝不混写 |
| `count` 比水位小 | 拒绝拉取 + ERROR 日志 |
| 水位文件损坏 | 拒绝拉取（**绝不从头重拉**——那会造成整文件重复行）；修复或删除后下轮重来 |
| 服务重启 | 启动立即补拉一轮 |
| 网页读到坏的水位文件 | 跳过该条目，不显示假进度 |
