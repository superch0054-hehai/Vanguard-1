# 现场部署方案（三设备拓扑）

已确认的现场设备：

```
① 电池柜（含中位机和通道，接电池）
② 装有 BTS Client + TestAPI 的 Windows 主机
③ 边缘算力盒子（TY1200）
```

激活码已到手，下面是针对这个拓扑的部署方案。

---

## 一、结论先行：管道彻底出局，必须走 TCP

**理由**：命名管道是**本机内核对象**，物理上出不了这台电脑。
协议文档明确写着"管道通讯方式不支持操作远程电脑上的客户端"。

①②③ 是三台独立设备，其中 ① 电池柜通过新威自己的链路连到 ②，
**我们的程序跑在 ③ 上，要和 ② 对话，只有 TCP 一条路。**

```
③ 边缘算力盒子 ──── TCP 502 ────→ ② Windows 主机（BTS Client）
                   实验室局域网              │
                                            │ 新威私有链路
                                            ↓
                                     ① 电池柜（中位机 + 通道 + 电池）
```

顺带说明一个常见误解：**我们连的是 ② 上的客户端，不是 ① 电池柜。**
`getdevinfo` 会返回"服务器列表"，那是中位机的 IP —— 那些**不是**连接目标，
只是信息。TCP 只管连 ② 的 502 端口。

> 好消息：管道那些麻烦（管理员权限、内核完整性标签）**全部不用管了**。
> TCP 不需要管理员权限。

---

## 二、采集程序部署在哪台机器上（Windows 还是 Linux）

这是我们这个项目**第二个要定的架构问题**（第一个是管道还是 TCP，已定）。

### 2.1 先明确一件事：两边代码是同一套

采集程序是 Python 写的，**Windows 和 Linux 都能跑**，代码不用改。
所以这个决定**不是不可逆的** —— 先选一个跑起来，发现不合适再换，成本很低
（因为数据源已经抽象成一层接口，见《第一阶段实施计划》的任务 6.2）。

**所以不要在这上面纠结太久。** 下面给判断依据，帮你快速决定。

### 2.2 两个选项的对比

| 维度 | ② Windows 主机 | ③ 边缘盒子（Linux） |
|---|---|---|
| 连客户端的方式 | 同机，127.0.0.1（也可用管道） | 走 TCP 过网络 |
| **网络依赖** | ✅ 不依赖，最稳 | ⚠️ 依赖网络，抖动会中断 |
| **读原始 NDA 文件** | ✅ 直接读文件系统 | ⚠️ 需要配共享目录（SMB/NFS） |
| 数据落盘位置 | ② 的磁盘（本来就在存测试数据） | ③ 的磁盘 |
| 对 ③ 的资源占用 | — | 采集程序很轻，但**数据会占磁盘** |
| **对关键机器的干扰** | ⚠️ 要往跑测试的机器上装程序 | ✅ **完全不碰关键机器** |
| 装软件的门槛 | 可能要管理员权限，机器是实验室共用 | Linux 装 Python 很常规 |
| 做常驻服务 | 任务计划程序，能用但笨 | systemd，清爽 |
| 归属关系 | 数据源所在，但机器可能是实验室的 | 大模型团队的机器，要协调 |

### 2.3 推荐：第一阶段在 ③（Linux）上做

**理由（按重要性排）**：

1. **不碰关键机器。** ② 是实验室的核心设备 —— 它跑着 BTS Client，
   正在**记录所有正在进行的测试数据**。往这台机器上加一个长期运行的 Python 进程，
   万一它占了 CPU 或磁盘 IO，**可能影响测试数据记录**。
   而厂商文档已经明确警告过：内存超过 90% 会导致取到的数据不完整。
   **这台机器越干净越好。**

2. **一套代码、一个地方。** 我们现有的工具（`probe.py`、`neware_client.py`）
   全部按"从远程机器走 TCP"写的，直接可用。

3. **Linux 做常驻服务更清爽。** systemd 比 Windows 任务计划程序好管得多 ——
   自动重启、日志、开机自启都是一行配置。

4. **权限更容易。** 在 ③ 上装 Python、跑服务，不涉及实验室关键机器的管理权限。

### 2.4 但有一件事必须提醒

**网络依赖是 ③ 方案的代价。** 具体会在这些地方疼：

- 网络抖动 → 采集中断（可恢复，但要写重连逻辑）
- ② 的 IP 变了 → 静默断掉（所以必须设固定 IP）
- ② 关机/重启 → 采集失效（要能检测并等待恢复）

**这些都要在代码里处理**，不能假设网络永远好。上面说的"七个能力"里的
"断点续采 / 自动重连"就是为这个准备的。

### 2.5 什么时候该改用 ②

出现下面任一条，就考虑把常驻服务下沉到 ②：

| 信号 | 说明 |
|---|---|
| 网络经常断，重连也救不回来 | 说明物理链路不可靠 |
| 数据量太大，③ 的磁盘装不下 | 一次循环测试明细可能几百万行；③ 的盘还要给大模型用 |
| 需要频繁直接读 ② 上的原始 NDA 文件 | 配共享目录不如干脆同机 |
| ③ 上要跑大模型，磁盘/IO 实在紧张 | 让 ③ 专心做推理 |

**如果改用 ②，有一条硬要求**：采集程序必须**资源克制** ——
限速、别做重查询、别把磁盘占满。因为它和正在记录测试数据的客户端抢资源。

### 2.6 一个介于两者之间的做法（推荐考虑）

不必非此即彼，可以**分层**：

```
② Windows 主机
   ├── BTS Client（必须常开）
   ├── 原始 NDA 文件（客户端自动备份写在这里，只进不改）
   └── （可选）一个轻量 Agent：只负责把新数据取下来、推到 ③

        ↓ 网络（只传解析后的数据，不传原始大文件）

③ 边缘盒子（Linux）
   ├── 采集控制逻辑 + 解析 + 落 Parquet
   ├── normalized / derived 数据
   └── 大模型 / Agent
```

**这样分配的好处**：原始数据留在数据源旁边（不折腾大文件过网络），
③ 上只放解析后的结果（体积小两个数量级）。
**代价**：多一层组件，复杂度上升。**Demo 阶段不建议**，等跑通了再考虑。

### 2.7 结论：每台机器上分别要做什么

| 事项 | 在哪台机器 | 频率 |
|---|---|---|
| 激活 API、重启客户端 | ② | 一次性 |
| 设固定 IP、放行防火墙 502 | ② | 一次性 |
| 跑官方 TestAPI 验证 | ② | 一次性 |
| **装采集程序、跑采集** | **③** | 持续 |
| 数据落盘（normalized / derived） | ③ | 持续 |
| 原始 NDA 文件 | ②（客户端自动写） | 自动 |
| 大模型 / Agent | ③ | — |

**一句话**：**② 只做一次性配置和跑客户端；日常的采集程序跑在 ③。**

## 三、网络层要做的四件事（都在 ② 上操作）

| # | 做什么 | 为什么 |
|---|---|---|
| 1 | 记下 ② 的 IP 地址，**并设为固定** | 我们的程序要写死这个 IP；如果哪天 DHCP 换了地址，采集服务就静默断掉了 |
| 2 | **放行防火墙 502 入站** | 异机时这个必做。同机不用管，异机不做就是"连接超时"（包被静默丢弃） |
| 3 | 确认 502 没被别的程序占用 | 一个端口同时只能一个程序用。被占了客户端就监听不了 |
| 4 | 在 ③ 上 ping ② 确认可达 | 先确认网络本身通，再谈协议。ping 不通就别往下走了 |

具体操作（在 ② 上）：

- 查 IP：`Win+R` 输入 `cmd`，然后 `ipconfig`，找"IPv4 地址"
- 查 502 占用：`netstat -ano | findstr :502` —— 有输出说明被占用了，记下 PID 用任务管理器查是哪个程序
- 放行防火墙：控制面板 → Windows Defender 防火墙 → 高级设置 → 入站规则 → 新建规则 → 端口 → TCP 502 → 允许
  （或者临时测试时先把防火墙关掉，验证通了再按规则放行）

## 四、分两步验证（顺序很重要）

### 第一步：在 ② 本机上验证"客户端 + API + 设备"是好的

**在 ② 上**运行官方 TestAPI，连本机的客户端，点【设备信息】→【发送】。

这一步**不涉及网络**，纯粹验证：客户端跑起来了、API 激活了、能读到设备。

| 结果 | 说明 |
|---|---|
| 有正确返回 | 客户端这一侧没问题，可以进入第二步 |
| 没返回 | 网络还没参与进来，问题就在客户端本身。查：客户端是否运行、API 是否激活、**激活后重启过没有** |

**为什么先做这一步**：把"客户端问题"和"网络问题"分开。
如果直接从 ③ 测试失败了，你分不清是哪一侧的问题。这一步先排掉一侧。

### 第二步：从 ③ 上验证"网络 + 协议"

在 ③ 上运行我们的工具：

```bash
# 先确认网络可达
ping <②的IP>

# 再做全面体检
python probe.py --transport tcp --host <②的IP>
```

**看错误信息就能定位问题在哪一层**（这是我特意做的区分）：

| 报错 | 含义 | 该做什么 |
|---|---|---|
| **连接被拒绝**（收到 RST） | 包到了 ②，但 502 端口没人监听 | 网络是通的。查客户端是否运行 / API 是否激活 / 端口是否被占 / 客户端版本是否 ≥2023/3/17 |
| **连接超时**（无响应） | 包被静默丢弃 | 网络层问题。查 IP 是否写错 / 是否同网段 / **防火墙是否放行 502** |
| ping 不通 | 网络根本不通 | 先解决网络：网线、交换机、网段、VLAN |
| 连上了但收不到回应 | 连接层没问题，应用层问题 | 命令格式（大小写）、或"联机消息"没发（见 CHECKLIST.md 第五节） |

## 五、数据怎么进边缘盒子：两条路，互补使用

这是"数据采集"的核心决策。**两条路都要用，不是二选一。**

### 路径 A：API 实时拉（已实现）

```
③ → TCP 502 → ② 客户端 → download / downloadStepLayer → 数据回到 ③
```

| 优点 | 缺点 |
|---|---|
| 实时，可以边测边看 | 一次最多 1000 条，要翻页 |
| 能拿工步层汇总（**自带 DCIR**），算 SOH 最省事 | 一次只能要一个通道 |
| 可以随时拉，不依赖测试结束 | 客户端必须一直开着 |

**适合**：进度监控、工步层汇总、增量采集、演示。

### 路径 B：NDA 文件自动回传（强烈建议现在就开）

`start` 命令支持一个 `backup` 节点，让客户端在**测试结束后自动把数据导出到指定目录**。

```bash
python neware_client.py --transport tcp --host <②的IP> start \
    "25-41-1-1:D:\\stepManager\\test\\1.xml:D672035TAA11:SC20-第3批" \
    --backup-dir "D:\\NewareBackup" --backup-type nda
```

这样客户端会在测试结束时把 NDA 文件写到 `D:\NewareBackup`，
文件名用**电池条码**命名（`filenametype=1`），便于和电芯对应。
然后 ③ 通过共享目录读取这些文件，用 `fastnda` + BDF 解析（见《Neware_NDA解析与_BatteryLab接入方案》）。

| 优点 | 缺点 |
|---|---|
| 拿到**完整原始数据**，不用翻页 | 只能整份拿，不能只要一部分 |
| 是原始证据，符合"Raw 永久保留"原则 | 需要配置共享目录 |
| 测试结束自动产生，不占通讯带宽 | |

> **强烈建议：从现在开始，每次启动测试都带上 `--backup-dir`。**
> 理由：**历史数据无法追溯补录**。如果某个测试当时没开自动备份，那次的
> 原始 NDA 文件就永远丢了，你只能拿到 API 拉下来的部分数据。
> 而开启成本几乎是零 —— 就在 `start` 命令上加两个参数。

### 两条路怎么配合

```
测试进行中  →  路径 A：轮询 getchlstatus 看进度，用 inquire 看实时读数
测试刚结束  →  路径 A：inquiredf 确认数据上传完整，download_stepLayer 拿汇总算 SOH
测试结束后  →  路径 B：读 NDA 文件做完整归档和原始证据保全
历史数据    →  路径 B：批量回灌
```

## 六、测试机控制：需要准备什么

你的职责里有"控制"这一半，这部分需要的东西和采集不一样。

### 5.1 工步文件（最关键，也最容易漏）

`start` 命令需要一个**工步文件的路径**，例如 `D:\stepManager\test\1.xml`。

**这里有两个必须搞清的点：**

1. **这个路径是 ② Windows 主机上的路径**，不是 ③ 边缘盒子上的路径。
   因为文件是客户端在自己那台机器上读的。
   **写成边缘盒子上的路径会直接失败。**

2. **工步文件从哪来？** 这是测试程序的定义（"恒流充电到 4.2V → 搁置 10 分钟 → 恒流放电到 3.0V"）。
   通常由研究人员在 BTS Client 的工步编辑器里做好。需要问清楚：
   - 放在哪个目录？
   - 命名规则是什么？
   - 谁负责维护？新增测试种类时谁来做文件？
   - 能不能用程序生成？（如果不能，自动化控制就有个人工环节）

### 5.2 电池条码（barcode）

`start` 时每个通道要下发一个条码，就是**电池的身份证号**。
这是把数据和"哪颗电池、哪次实验"关联起来的关键。

需要一张 **通道 ↔ 条码** 的对应表。如果现场是靠人工扫码贴标签的，就要问清楚这个流程。

### 5.3 控制命令清单

协议里可用的控制操作（我们的工具都已实现）：

| 操作 | 命令 | 用在哪 |
|---|---|---|
| 启动测试 | `start` | 下发工步文件 + 条码 + 备注，可同时启动多个通道 |
| 停止 | `stop` | 正常停止 |
| 广播停止 | `broadcaststop` | 一台设备下所有通道一起停（紧急情况用） |
| 接续 | `continue` | 暂停后继续 |
| 跳转 | `goto` | 跳到指定工步 |
| 通道开关 | `chl_ctrl` | IGBT 设备的通道通断（需硬件支持） |
| 重置工步 | `reset` | 重新下发工步文件 |
| 点灯 | `light` | 点亮通道指示灯，方便现场找到通道 |
| 预约暂停 | `setpause` / `cancelpause` / `getpause` | 定时暂停 |
| 监看状态 | `getchlstatus` | 看通道是测试中/停止/保护/完成 |
| 实时读数 | `inquire` | 看当前电压电流 |

常用命令示例：

```bash
# 启动测试（带备注和自动备份）
python neware_client.py --transport tcp --host <IP> start \
    "25-41-1-1:D:\\stepManager\\test\\1.xml:BAR001:SC20-第3批" \
    "25-41-1-2:D:\\stepManager\\test\\1.xml:BAR002:SC20-第3批" \
    --backup-dir "D:\\NewareBackup"

# 看状态
python neware_client.py --transport tcp --host <IP> status

# 等测试结束（轮询，默认等 finish/stop/protect）
python neware_client.py --transport tcp --host <IP> wait 25-41-1-1 --timeout 7200

# 停止
python neware_client.py --transport tcp --host <IP> stop 25-41-1-1
```

### 5.4 一个要注意的边界

**不要频繁调用 `inquire`。** 协议明确说实时性不优于 5 秒，
而且 API 文档提到查询条码会影响性能（`barcode=0` 可以不查）。

另外**不要频繁下发控制命令**。这台客户端同时在管着整个实验室正在跑的测试，
发命令太密可能影响它正常记录数据。

## 七、建议的采集服务流程

做成常驻服务时，主循环大致是这样：

```
每 N 秒循环一次：
  1. getchlstatus 拿所有通道状态
  2. 找出状态从 working 变成 finish/stop 的通道（说明这一轮测试结束了）
  3. 对每个刚结束的通道：
       a. inquiredf 确认数据上传完整（返回 true，且 count 不再增长）
          ★ 没传完就拉，会缺数据 —— 这是厂商文档里点名的坑
       b. download_steplayer 拿工步层汇总（算 SOH 用，数据量小）
       c. download_all 拿完整明细（按需，数据量大）
       d. 落 Parquet 文件 + 记录元数据（文件哈希、解析器版本、时间）
       e. 用 barcode 关联到"哪颗电池、哪次实验"
  3. 同时检查 ③ 上的共享目录，有没有新的 NDA 文件（路径 B）
  4. 记录本次循环的日志；出错要能看出来是网络问题还是客户端问题
```

两个关键设计点：

- **状态变化检测**：不要每次都拉全量数据（太慢也太重），而是靠 `getchlstatus`
  的状态变化触发。`finish`（正常跑完）和 `stop`（人为或异常停止）要区分处理，
  两者的业务含义不同。
- **失败要能区分层次**：网络断了（超时）和客户端重启了（拒绝/管道断开）要分开处理，
  前者等待重试，后者要重新建立连接。我的工具在错误信息里已经做了区分，服务层直接用即可。

## 八、今天就能做的事

在 ② 上（Windows 主机）：

1. 【帮助 → 模式设置】填入注册码 → 点激活 → **重启客户端**（别忘）
2. 悬停【已激活】确认能看到 `API` 字样
3. 记下 IP，设为固定；`ipconfig` 看一下
4. 放行防火墙 502
5. 用官方 TestAPI 点一下【设备信息】→【发送】，确认客户端侧是好的
6. 问清楚：工步文件放在哪个目录、谁维护；通道和条码怎么对应

在 ③ 上（边缘盒子）：

7. 确认操作系统是什么（很可能 Linux）；装 Python 3.9+
8. `ping <②的IP>` 确认可达
9. 把 `neware_comms` 目录拷过去
10. 跑 `python neware_client.py --transport tcp --host <②的IP> info`

第 10 步能看到通道清单，就说明**路通了** —— 第一层验收过了。

## 九、部署时别忘的三件事

| 事项 | 为什么 |
|---|---|
| **客户端开机自启** | 实验室的人会关机器。客户端不启动，采集服务就全断了 |
| **采集服务断线自动重连** | 客户端是会被重启的真实设备。断线后要能自动重连并继续，不能崩掉等人来手动启 |
| **写一份部署说明** | 写清 IP、端口、路径、管理员要求、常见故障。接手的人不用重新踩一遍坑 |

---

## 十、还需要确认的四件事

| 事项 | 为什么要 | 影响 |
|---|---|---|
| ② 的 IP 地址 | 程序要连的目标 | 阻塞第一步验证 |
| ② 上客户端的版本号（帮助 → 关于） | TCP 需要 ≥2023/3/17 | 版本太老则 TCP 也不可用，那就得换方案（比如只走 NDA 文件路线） |
| ③ 操作系统的类型和版本 | 决定 Python 环境怎么装 | 影响部署方式 |
| 工步文件的目录与维护方式 | 启动测试要用 | 影响控制能否自动化 |

其中**第二项是风险点**：如果客户端版本太老、又必须跨机器，那 API 路线就走不通了，
只能退回"纯 NDA 文件路线"（客户端手动或定时导出 → ③ 解析文件）。
这条退路也是可行的，但实时控制和实时监控就没有了。

建议**先确认版本号**，再决定投入多少精力在 API 路线上。
