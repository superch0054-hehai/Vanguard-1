# 你要交什么：数据采集交付物说明

**职责边界**：只负责把原始数据**完整、正确地拿到并落盘**。
不算 SOH 指标、不做报告、不做 Agent —— 那些是下游的事。

这份文档定义：交什么、长什么样、怎么算做完了。

---

## 一、一句话

**你交的不是"一段代码"，而是一套"能把数据可靠地变成资产"的东西：**

```
采集程序  +  数据规范（长什么样、字段什么意思）  +  验收证据（凭什么说它完整正确）
```

三段缺一不可。**只有程序没有规范和证据，下游不敢用你的数据。**

---

## 二、核心问题："完整、正确"必须可检验

"完整"和"正确"是形容词。交付时你不能说"我觉得挺完整的" ——
必须能拿出**可检验的标准**。下面这些就是标准。

### 2.1 "完整"的六个检验点

| # | 检验什么 | 怎么检 | 不通过意味着 |
|---|---|---|---|
| 1 | **数据已上传完** | `inquiredf` 返回 `true` 且 `count` 不再增长 | 中位机还在往上传，这时拉会缺尾巴 |
| 2 | **行数一致** | 采集到的行数 == BTSDA 导出的行数 | 分页漏了、或提前停了 |
| 3 | **序号连续无缺** | `seqid` 从小到大连续，无跳号 | 中间丢了一段 |
| 4 | **循环/工步齐全** | cycle 数、step 数与工步层数据一致 | 工步层和明细对不上，说明口径或采集有问题 |
| 5 | **时间覆盖完整** | 首末 `atime` 覆盖整个测试时段 | 只采到了一部分 |
| 6 | **所有目标通道都采了** | 通道清单逐个核对，没有遗漏 | 漏采某个通道 |

### 2.2 "正确"的四个检验点

| # | 检验什么 | 怎么检 |
|---|---|---|
| 1 | **和官方软件对账一致** | 用 BTSDA 导出同一测试，逐字段比：电压、电流、容量、能量、循环数、首末值 |
| 2 | **口径已确认并记录** | 时间单位（ms 还是 s）、容量口径（每步累计还是整圈）、辅助通道含义（T1 是温度还是别的），全部写进文档 |
| 3 | **数值在合理范围** | 电压不在离谱范围、温度不是负数、容量单调增长（同一工步内） |
| 4 | **空值/异常已处理** | 缺失的辅助通道、异常值，是丢弃、填 0 还是保留？规则明确 |

> **第 1 条是王道。** 只要和 BTSDA 一致，其他三条基本自动成立。
> 所以"建金标准数据集对账"是第一阶段最重要的工作。

### 2.3 "可重复、可追溯"的三个检验点

| # | 检验什么 | 为什么 |
|---|---|---|
| 1 | **原始文件永久保留、不修改** | 原始数据是唯一证据，解析结果都可以重生成，原始文件丢了就没了 |
| 2 | **解析结果能重建** | 记录：采集时间、解析器版本、协议版本、原始文件哈希。换台机器用同样输入能得同样输出 |
| 3 | **采集过程有日志** | 出问题时能查"某次为什么漏了"，而不是靠猜 |

## 三、你在代码里要做出什么

### 3.1 一个采集程序，具备这七个能力

| 能力 | 说明 | 优先级 |
|---|---|---|
| **1. 发现** | 知道有哪些通道、哪个测试跑完了 | 必须 |
| **2. 等待完整** | 拉数据前先 `inquiredf` 确认上传完 | 必须 |
| **3. 分页拉全** | `download` 一次最多 1000 条，要自动翻页到底 | 必须 |
| **4. 落盘** | 存成 Parquet（明细）+ 附元数据 | 必须 |
| **5. 关联电池** | 用条码把数据绑定到"哪颗电池、哪次实验" | 必须 |
| **6. 幂等** | 同一份数据重复采，不会产生重复或损坏 | 重要 |
| **7. 断点续采 / 自动重连** | 中途断了能接着采，网络抖动能自己恢复 | 重要 |

### 3.2 数据要落成什么样（目录结构）

建议直接沿用项目既定的分层（《Neware NDA 解析与 BatteryLab 接入方案》里提的），
这样将来接上层不用改：

```
/data
├── raw/                    ★ 原始文件，永久保留，绝不修改
│   └── 2026-10-01/
│       └── BAR001_25-41-1-1_testid71.ndax
│
├── normalized/             ← 解析后的完整时序数据（明细）
│   └── channel=25-41-1-1/testid=71/detail.parquet
│
├── derived/                ← 汇总数据（工步层，算指标的人主要看这个）
│   └── channel=25-41-1-1/testid=71/steps.parquet
│
├── manifest.db             ← 索引：哪份数据在哪、对应哪颗电池、什么状态
└── logs/                   ← 采集日志
```

**为什么分三层**：

- `raw/` 是**原始证据**，只进不改。将来口径变了、解析器升级了，还能从它重新生成
- `normalized/` 是可以重生成的**解析结果**
- `derived/` 是给下游用的**汇总**，数据量小两个数量级

### 3.3 每份数据必须附带的元数据（这是"可追溯"的全部）

| 字段 | 例子 | 为什么 |
|---|---|---|
| `dataset_id` | 20261001-254111-t71 | 唯一标识 |
| `channel` | 25-41-1-1 | 哪个通道 |
| `barcode` | BAR001 | **哪颗电池** |
| `testid` | 71 | 哪次测试 |
| `collected_at` | 2026-10-01 09:15:33 | 什么时候采的 |
| `source` | api / nda_file | 从哪条路采的 |
| `raw_sha256` | d3f5...a7e9 | 原始文件哈希 |
| `parser_version` | neware_client 0.1 | 用什么版本解析的 |
| `protocol_version` | 1.19 | 对哪个协议版本 |
| `client_version` | 8.0.0.581 | 现场客户端版本 |
| `row_count` | 1_284_371 | 行数 |
| `time_range` | 2026-09-28 10:00 ~ 2026-09-30 22:00 | 时间覆盖 |
| `cycle_count` | 100 | 循环数 |
| `time_unit` | ms | **testtime 的单位，必须记** |
| `validation` | {完整性: pass, 对账: pass} | 校验结果 |

### 3.4 还要交一份"字段字典"

这是最容易被忽略、但对下游最值钱的东西。用大白话写清每个字段**是什么、单位、什么口径**：

| 字段 | 含义 | 单位 | 口径（容易搞错的地方） |
|---|---|---|---|
| `seqid` | 数据序号 | — | 从 1 开始，连续 |
| `stepid` | 工步号 | — | 同一循环内可重复出现 |
| `cycleid` | 循环号 | — | — |
| `steptype` | 工步类型 | — | `cc`恒流充 `dc`恒流放 `rest`搁置…共 17 种 |
| `testtime` | 本工步已运行时间 | **毫秒** | ⚠️ 注意是 ms，不是秒 |
| `atime` | 绝对时间 | — | 真实世界时刻 |
| `volt` | 电压 | V | — |
| `curr` | 电流 | A | 放电为负还是正？**要现场确认** |
| `cap` | 容量 | Ah | ⚠️ **该工步内的累计值，不是整圈的** |
| `eng` | 能量 | Wh | 同上，工步内累计 |
| `V1`/`T1`/`Thk1` | 辅助通道 | ? | ⚠️ **列名随硬件变化，含义需现场确认** |

**别小看这份表。** 下游算指标的人如果不知道 `cap` 是"工步内累计"，
直接对全表取最大值，算出来的容量保持率就是错的 —— 而且他不会发现。
**你的字段字典是防止这类错误的唯一屏障。**

## 四、怎么算做完了（验收清单）

这份清单可以直接拿去当交付验收表，每项都要有证据。

### A. 功能验收

| # | 项 | 证据 |
|---|---|---|
| A1 | 能列出所有通道 | `info` 的输出 |
| A2 | 能对一个指定测试拉全明细 | 行数 + 文件 |
| A3 | 能拉工步层汇总（含 DCIR） | 文件 + 前几行 |
| A4 | 拉之前会确认数据上传完整 | 日志里的 `inquiredf` 记录 |
| A5 | 数据落成 Parquet 且带元数据 | 文件 + 元数据样例 |
| A6 | 数据能关联到电池条码 | manifest 里的对应关系 |

### B. 完整性验收

| # | 项 | 证据 |
|---|---|---|
| B1 | 行数与 BTSDA 一致 | 对账表 |
| B2 | `seqid` 连续无跳号 | 校验脚本输出 |
| B3 | cycle/step 数与工步层一致 | 校验脚本输出 |
| B4 | 所有目标通道都采到了 | 通道清单逐项打勾 |

### C. 正确性验收

| # | 项 | 证据 |
|---|---|---|
| C1 | 与 BTSDA 逐字段对账通过 | **对账报告**（最重要） |
| C2 | 字段字典已交付 | 文档 |
| C3 | 时间单位已用真实数据验证 | probe 输出的 `testtime 单位判定` |
| C4 | 数值范围合理 | 校验脚本输出 |

### D. 可靠性验收

| # | 项 | 证据 |
|---|---|---|
| D1 | 重复采同一份数据，结果一致且不重复 | 两次运行的文件哈希对比 |
| D2 | 中途断网后能恢复 | 人为断网测试的记录 |
| D3 | 客户端重启后能自动重连 | 重启客户端后的日志 |
| D4 | 跑一整晚无异常 | 一晚上的日志 |

### E. 交付文档

| # | 项 |
|---|---|
| E1 | 部署说明（装在哪、依赖什么、怎么启动） |
| E2 | 使用说明（怎么跑一次采集、怎么加新通道） |
| E3 | 字段字典 |
| E4 | 故障排查（报什么错代表什么） |

## 五、明确不做什么（避免范围蔓延）

| 不做 | 谁做 |
|---|---|
| 算容量保持率、库仑效率、DCIR 等指标 | 下游 |
| 生成 SOH 报告、画图、排版 | 下游 |
| Agent / 大模型编排 | 别人 |
| 把数据同步到别的地方（云端/其他库） | 视需要，不属于采集 |
| 修改或清洗原始数据 | **谁都不该做** —— 原始数据只进不改 |

**关于"测试机控制"**：你说只负责采集，那控制要么是别人做，要么是你顺带做。
如果是你顺带做，只有一个注意点 —— **启动测试时一定要带自动备份参数**
（`--backup-dir`），这样能多一份原始 NDA 文件。
理由还是那句：**历史数据无法追溯补录，当时没开就永远丢了。**

## 六、三周怎么做完（分阶段）

| 阶段 | 产出 | 天数 |
|---|---|---|
| **一、跑通** | 能手动跑一次：列通道 → 拉数据 → 落 Parquet | 1～2 天 |
| **二、拉全拉对** | 分页拉全、等上传完、序号连续性校验 | 2 天 |
| **三、对账** | 与 BTSDA 对账通过，产出对账报告 + 字段字典 | 2 天 |
| **四、能重复跑** | 状态变化触发、幂等、断线重连、跑一整晚 | 2～3 天 |
| **五、交付文档** | 部署说明、使用说明、字段字典、故障排查 | 1 天 |

**最小可用版本（如果时间紧张）**：一到三阶段。
即"能手动跑、能拉全、能证明数据是对的" —— 这已经能让下游开始干活了。
四、五阶段是"能长期无人值守"和"能交接给别人"，可以往后放。

**但第三阶段不能省。** 没有对账，你无法证明数据正确，
下游算出来的指标对不对也就无从判断 —— 整个报告的可信度就没了。

## 七、你的交付物最终清单

```
1. 采集程序（代码）
2. 数据目录（raw / normalized / derived + manifest + logs）
3. 字段字典  ← 容易被忽略，但对下游最值钱
4. 对账报告（API 数据 vs BTSDA 官方导出）  ← 证明"正确"
5. 完整性校验结果（行数、序号、循环数、通道覆盖）  ← 证明"完整"
6. 部署与使用说明
7. 故障排查说明
```

**给别人一句话介绍你做完了什么**：

> "测试跑完后，数据会自动被完整采下来，落成 Parquet 并关联到具体电池；
> 原始文件永久保留。数据已和 BTSDA 官方导出逐字段对账通过，
> 字段口径写成文档了。下游可以直接按目录约定读取。"
