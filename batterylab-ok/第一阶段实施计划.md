# 第一阶段实施计划顾问的原话：> "windows 只是第一阶段，测试机的数据都是在上面生成的，我们要从 windows 上获取数据源，> 才会用到。如果后期，我们能够直接和测试机通讯，其实也就没 windows 的机器什么事情了"这段话读出来的路线图是：```第一阶段：③ ← TCP ← ② Windows ← 测试机      （现在，Windows 是必经的中转）后期    ：③ ←──── 直接 ────────→ 测试机      （去掉 ②，效率更高）```---## 一、先讲三件事### 1.1 这条消息不改变你现在该做什么现在只有 Windows 这条路可走 —— 测试机不对外开放文档化的接口。所以第一阶段的动作和之前一样，**照做即可**。而且顾问说"数据是在测试机上生成的"，这跟我们之前在协议文档里挖到的线索**是一致的**：`getdevinfo` 返回的"服务器"列表里，IP 是 `.35` / `.36`，端口是 `3306`（MySQL）；而通道的 IP 也是 `.35` / `.36`。说明**跑 MySQL 的那台机器就是挂在通道上的中位机**，也就是测试机的一部分。数据生成在那里，Windows 上的客户端去读它。### 1.2 ⚠️ 但这里藏着一个必须早验的风险协议里 `download`（下载历史明细）、`download_stepLayer`、`downloadlog` 三条命令都写着同一句限制：> "只下载**服务器 127.0.0.1** 下的测试数据"`inquiredf` 也写"只支持查询 127.0.0.1 服务器"。**现在这句话的含义变得微妙了**：| 情况 | `download` 能用吗 ||---|---|| ② 上同时跑着客户端和服务器（数据在 ② 本机） | ✅ 能用 || 数据在测试机（中位机）的 MySQL 上，② 只是远程连它 | ⚠️ **可能拿不到历史明细** |**这是个会决定方案走向的风险，必须在第一阶段前几个任务里验掉。**- 如果 `download` 能用 → 按原计划走- 如果不能用 → 那就只剩：`inquire`（实时数据，但拿不到历史）+  NDA 文件路线（让客户端导出文件），或者**加速推进"直连"**  —— 而"直连"在这里不再是我之前说的"逆向私有格式"，而是  **连一个标准的 MySQL**，性质完全不同（见 1.3）**好消息是**：验它只需要一条命令，就在下面的任务 3 里。### 1.3 顾问的话让"直连"这条路更具体了我上次的分析说"不建议直连"，理由是 schema 私有、要逆向。但结合顾问这句话重新看：**如果数据就在测试机的 MySQL 里，那"直连" =用标准 MySQL 客户端连过去查**，而不是逆向硬件协议。性质上的区别：| | 我之前担心的 | 现在看起来更可能的情况 ||---|---|---|| 连的是什么 | 逆向出来的私有二进制协议 | **标准 MySQL（3306）** || 需要什么 | 逆向固件/协议 | **表结构文档 + 授权** || 风险 | 固件升级就废 | 表结构变化，但标准接口稳定 |所以要问厂商的问题也该变一变，重点从"能不能给个接口"变成：1. **测试机上的 MySQL 是否允许外部只读访问？**2. **表结构文档能否提供？**3. 并发查询会不会影响正在进行的测试？这些问题的答案，**只有在第一阶段跑出 `getdevinfo` 的结果之后才好问** ——因为你要先知道"服务器"的 IP 和端口到底是什么。### 1.4 所以第一阶段还要多产出一个东西既然知道将来要换数据源，**现在就该在代码里留一个口子**，让"数据从哪来"变成可替换的细节。不用做复杂的架构，就是一个模块、一个接口的事（见第四节）。成本很低，但如果现在不留，将来换数据源时上层的 SOH 计算、报告生成、Agent 全都要改。**更重要的一个观念**：第一阶段用 API 建起来的这套数据和结果，**不是白做的** —— 它是将来验证"直连拿到的数据对不对"的**唯一基准**。没有它，你换成直连之后无法证明数据是对的。---## 二、第一阶段的目标与产出### 目标**能从 ③ 上稳定读到 ② 的数据，并把数据落到本地、能重复跑。**### 产出四样东西| # | 产出物 | 用来证明什么 ||---|---|---|| 1 | 一份《现场信息记录》 | ② 的 {}while True:    现在 = getchlstatus(所有通道)    for 通道 in 现在:        # 从"测试中"变成"结束" → 这一轮刚跑完        if 上一轮.get(通道) == "working" and 现在[通道] in ("finish", "stop"):            采集(通道)    上一轮 = 现在    sleep(30)      # 不要比 5 秒更短，协议实时性不优于 5 秒def 采集(通道):    while not inquiredf(通道).完整:      # 没传完就拉会缺数据        sleep(10)    汇总 = download_steplayer(通道)      # 数据量小，算 SOH 靠它    明细 = download_all(通道)            # 数据量大，按需    落成_parquet(汇总, 明细)    记录元数据(文件哈希, 采集时间, 解析器版本, 通道, 条码)```**边界**：不要频繁调 `inquire`，也不要频繁下发控制命令 ——这台客户端同时在管整个实验室的测试，命令太密可能影响它正常记录数据。#### 6.2 数据访问层：为将来的"直连"留口子就是这个思路，一个文件、一个接口：```python# datasource.py —— 数据访问层class DataSource:    """数据源接口。今天用 API 实现，将来可以换成直连实现，上层不用改。"""    def list_channels(self) -> list[Channel]: ...    def get_realtime(self, ch) -> dict: ...    def get_step_summary(self, ch, testid=0) -> list[dict]: ...    def get_detail(self, ch, testid=0) -> list[dict]: ...class ApiDataSource(DataSource):    """现在：走 TCP 502 的官方 API。"""    def __init__(self, host, port=502): ...# 将来直连测试机时，只需要再加一个实现：# class DirectDataSource(DataSource):#     """将来：直连测试机的 MySQL。"""#     def __init__(self, db_host, db_port=3306): ...```**这样带来的好处**：上层的 SOH 计算、报告生成、Agent 全都不用改。换数据源只是换一个 `DataSource` 的实现类。**顺便建议**：数据落到本地后，用 **DuckDB** 在上面建视图 ——这样你在本地就能用 SQL 随便查（聚合、关联、画曲线），**既得到了"直连数据库"的全部便利，又完全不碰厂商的库，口径还是 API 的**。**验收**：让它跑一晚上，第二天能确认 ——① 每个跑完的测试都有对应的数据文件；② 数据能关联到通道和条码；③ 中途网络抖动能自己恢复。---## 四、时间安排| 天 | 任务 | 备注 ||---|---|---|| D1 上午 | 任务 1（自己） | 同时把"要问别人的三件事"发出去 || D1 下午 | 任务 2（自己） | **记录
