# 现场首次尝试：操作步骤

**目标**：用笔记本的 Ubuntu（WSL）作为算力盒子的替身，打通到 ② Windows 主机的通讯。

**安全说明**：下面只用到**只读命令**（`getdevinfo` / `getchlstatus` / `inquire` /
`download` / `downloadStepLayer` / `inquiredf` / `downloadlog`）。
**不会调用 `start` / `stop` / `goto` / `reset`**，所以不会影响正在跑的测试。

---

## 全程概览

```
【阶段 A】在 ② Windows 主机上        （约 15 分钟，一次性配置）
   A1 查 IP
   A2 查客户端版本
   A3 激活 API 并重启
   A4 验证激活
   A5 查 502 端口占用 + 内存
   A6 放行防火墙 502
   A7 ★ 用官方 TestAPI 点"设备信息"   ← 关键关卡
   A8 顺手记录现场信息（条码对应表、工步目录）

【阶段 B】在你的笔记本上
   B1 Windows 侧先测网络可达        ← 把"网络问题"和"WSL 问题"分开
   B2 进 WSL，测 ping 和 502
   B3 跑自测确认工具没问题
   B4 跑 info 拿设备信息
   B5 跑 probe 全面体检
```

**顺序很重要**：A7 是分水岭。它不涉及网络，纯粹验证"客户端 + API 激活 + 能读到设备"。
A7 不过，后面都不用谈。

---

# 阶段 A：在 ② Windows 主机上

## A1. 查 IP

在 ② 上打开 `cmd`（Win+R 输入 `cmd`），执行：

```
ipconfig
```

找到**你正在用的那块网卡**（一般叫"以太网"或"WLAN"）下面的 `IPv4 地址`，
形如 `192.168.1.20` 或 `10.x.x.x`。

**→ 把这个 IP 记下来，后面全程要用**（记为 `<②IP>`）。

## A2. 查客户端版本

客户端菜单栏 →【帮助】→【关于】，记下版本号。

**→ 必须 ≥ 2023/3/17**。低于这个版本，TCP 方式用不了。
（如果太老：要么找新威升级，要么只能用 NDA 文件路线，得改方案。）

## A3. 激活 API

1. 菜单栏 →【帮助】→【模式设置】
2. 在"激活码"框里填入注册码
3. 点【激活】
4. **重启客户端**（最容易忘的一步，不重启不生效）

## A4. 验证激活

重新打开【帮助】→【模式设置】，把鼠标**悬停在【已激活】上**，
应该显示带 `API` 字样的注册模式。

**→ 看不到 API 字样就别往下走了。** 检查：注册码是否完整、是否重启过、
注册码是否和这台机器绑定。

## A5. 查端口占用和内存

```
netstat -ano | findstr :502
```

**→ 应该没有任何输出**（没被占用）。
如果有输出，记下最后一列的 PID，用任务管理器查出是哪个程序，
关掉它（否则客户端没法监听 502）。

同时打开任务管理器看**内存占用**，**确认低于 90%** ——
厂商文档明确说内存超过 90% 会导致取到的数据不完整。

## A6. 放行防火墙 502

**这一步最容易卡住。** Windows 防火墙默认会拦掉外部对 502 的访问。

**正规做法**：控制面板 → Windows Defender 防火墙 → 高级设置 →
入站规则 → 新建规则 → 端口 → TCP → 特定本地端口填 `502` → 允许连接 →
全部勾选（域/专用/公用）→ 命名保存。

**如果想先快速试通**（临时的）：

```
netsh advfirewall set allprofiles state off
```

⚠️ 测完记得开回来：

```
netsh advfirewall set allprofiles state on
```

**为什么重要**：防火墙拦掉的表现是**连接超时**（包被静默丢弃），
而客户端没启动的表现是**连接被拒绝**。这两个现象排查方向完全不同 ——
所以到阶段 B 时，看错误信息就能定位是哪一侧的问题。

## A7. ★ 关键关卡：用官方 TestAPI 点一下

启动新威给的 **TestAPI** 小程序 → 让它连上本机的客户端 →
点【设备信息】按钮 → 点【发送】。

| 结果 | 说明 | 下一步 |
|---|---|---|
| **输出框出现 `<cmd>getdevinfo_resp</cmd>`** | ✅ 客户端侧完全正常：已激活、能读到设备 | 进入阶段 B |
| 没有返回 | ❌ **问题在客户端本身**，跟网络无关 | 按下面排查 |

**没返回时的排查顺序**：
1. 客户端是不是开着？
2. API 是不是激活了？**重启过没有？**
3. TestAPI 是不是以**管理员权限**启动的？（管道方式必须）
4. 客户端日志里有没有线索？
5. 命令内容和协议文档**逐字对得上吗**（大小写！）

## A8. 顺手把现场信息记下来

趁在现场，一次问清楚（这些后面都要用）：

| 要问的 | 为什么要 |
|---|---|
| **通道 ↔ 电池条码对应表** | 没有它，数据没有归属，算不出"哪颗电池" |
| 工步文件（.xml）放在哪个目录、谁维护 | 后面做控制要用 |
| 哪些通道现在是空闲的 | 将来做控制验证要用（**现在别碰**） |
| 客户端和测试柜是怎么连的（网线？串口？） | 理解拓扑 |

**注意**：`info` 命令会列出所有通道，你可以拿它的输出和现场核对。

# 阶段 B：在你的笔记本上

> 假设你已经配好 SSH/免密（之前体检时确认过 WSL 可用）。
> 如果还没把代码拷过去，先在 WSL 里执行：
> ```bash
> rsync -av --delete --exclude '.venv' --exclude '__pycache__' \
>   "/mnt/c/Users/gzz25/Desktop/电池/neware_comms/" ~/batterylab/
> ```

## B1. 先用 Windows 侧测网络可达（把问题分层）

在 Windows 的 **PowerShell** 里：

```powershell
Test-NetConnection <②IP> -Port 502
```

看 `TcpTestSucceeded` 那一行。

**为什么要先做这一步**：WSL2 用的是 NAT 网络，可能比 Windows 多一层问题。
**先在 Windows 上测，能把"网络不通"和"WSL 网络配置问题"分开。**

| 结果 | 含义 |
|---|---|
| `True` | Windows 能连上 → 网络和客户端都没问题，进 B2 |
| `False` 但能 ping 通 | 网络通、但 502 没响应 → **回 A5/A6**：客户端没监听，或防火墙拦了 |
| ping 都不通 | 两台机器不在同一网络 → 确认笔记本连的是哪个 WiFi/网段 |

## B2. 进 WSL，测 ping 和 502

```
wsl -d Ubuntu
```

```bash
ping -c 3 <②IP>

# 测 502 端口（不需要额外工具）
timeout 5 bash -c "echo > /dev/tcp/<②IP>/502" && echo "502 可达" || echo "502 不可达"
```

| 结果 | 下一步 |
|---|---|
| 都通 | 进 B3 |
| ping 通、502 不通 | 回阶段 A5/A6 |
| ping 不通 | WSL 的 NAT 问题 → 见文末"如果 WSL 连不上" |

## B3. 跑自测，确认工具没问题

```bash
cd ~/batterylab
source .venv/bin/activate
./selftest.py
```

**期望：`通过 81 项，失败 0 项`**（不需要网络和设备）。

**如果这里就失败**，说明是环境问题，别往下走 —— 先解决它。
这一步过了，就证明"我的代码本身没问题"，后面出问题一定是设备或网络侧的。

## B4. 拿设备信息

```bash
python neware_client.py --transport tcp --host <②IP> info
```

**期望**：列出服务器列表和所有通道，类似：

```
服务器（中位机）2 台，通道 16 个
  server 192.168.1.33:3306
  server 192.168.1.34:3306
  22-1-1-1@192.168.1.35  BTS80  可点灯=True
  22-1-1-2@192.168.1.35  BTS80  可点灯=True
  ...
```

**★ 这里有两个重要产出，第二个比第一个重要：**

**产出 A：通道清单**（四元组 `devtype-devid-subdevid-chlid`）—— 后面所有操作都要用它。

**产出 B：`serverip` 列表** —— 把里面的 IP 和 `<②IP>` 比一比：

| 看到的 | 说明 | 影响 |
|---|---|---|
| 含 `<②IP>`（或 127.0.0.1） | 数据库就在 ② 本机 | `download` 应该能用 |
| 全是别的 IP | **数据在测试机/中位机上**，② 只是远程连它 | ⚠️ `download` 可能拿不到历史明细，B5 要重点看 |

**这一步成功 = 第一层验收过了（连得上）。**

## B5. 全面体检

```bash
python probe.py --transport tcp --host <②IP> --limit 500
```

（`--limit 500` 是限制明细只拉 500 条，首次跑用这个更快；全量检查留到后面。）

它会依次检查 8 个环节，然后做单位校验和 SOH 预览。**重点看这几项**：

| 检查项 | 期望 | 不对说明什么 |
|---|---|---|
| 连接 / 设备信息 / 通道状态 / 实时数据 | PASS | — |
| **download（历史明细）** | **能拉到数据** | ⚠️ 若 0 条或报错 → 数据不在 ② 本机，历史明细这条路可能走不通 |
| downloadStepLayer | 有工步 | 同上 |
| `testtime 单位判定` | **ms** | 判定成 s 说明现场与文档不符，时间换算都要改 |
| 辅助通道列名 | 自动列出实际列名 | 列名随硬件变化，解析不能硬编码 |
| **SOH 预览** | **能算出容量保持率** | 算不出说明容量口径和现场不一致，**做报告前必须解决** |

**这一步过了 = 第二层验收过了（拿得到数）。**

## 如果卡住了：按错误信息定位

`probe.py` 和 `neware_client.py` 的错误信息是特意分层的，直接告诉你问题在哪：

| 报错 | 含义 | 去改什么 |
|---|---|---|
| **连接被拒绝（收到 RST）** | 包到了 ②，但 502 没人监听。**网络是通的** | 客户端是否运行 / API 是否激活 / 502 是否被占 / 版本是否够新 → **阶段 A3–A6** |
| **连接超时（无响应）** | 包被静默丢弃 | **防火墙没放行**（A6）/ IP 写错 / 不同网段 |
| ping 不通 | 网络根本不通 | 确认笔记本连的网络 |
| 连上了但收不到回应 | 连接层没问题，应用层问题 | 命令大小写；或"联机消息"没发（见 CHECKLIST 第五节） |
| 说"当前系统是 linux，不支持 Windows 命名管道" | 你在 Linux 上用了 `--transport pipe` | 改成 `--transport tcp` |

**这张表的价值**：不同的错误指向完全不同的排查方向，
**看错误信息，不要凭感觉猜。**

## 如果 WSL 连不上但 Windows 能连

WSL2 默认是 NAT 网络，有时访问局域网设备会有问题。两个办法：

**办法一：改用镜像网络模式**（推荐先试）

在 WSL 里编辑 `/etc/wsl.conf`（需要 sudo），加上：

```ini
[network]
networkingMode=mirrored
```

然后在 Windows 上执行 `wsl --shutdown`，再重新进 WSL。

**办法二：换回 Windows 开发**

VS Code 的 Remote-SSH 在两个系统上体验一样，
不要在 WSL 上死磕 —— 耽误时间不值得。
