# 如何调通：通关手册

这份文档只讲**要做什么、为什么这么做、怎么算过关**。
每关都用同样的四段式：**做什么 → 为什么 → 过关标志 → 卡住查什么**。

---

## 先说清楚：什么叫"调通了"

很多人以为"能连上"就算调通，其实要分三层。三层都过了才算真通：

| 层次 | 标准 | 意义 |
|---|---|---|
| **第一层：连得上** | 能问到设备信息，有正确返回 | 路通了，钥匙对了 |
| **第二层：拿得到数** | 能把某个通道的历史数据拉下来，条数和 BTSDA 官方导出对得上 | 数据是真的、全的 |
| **第三层：算得出指标** | 能用这些数据算出 SOH 指标（容量保持率等） | 报告有了数据基础 |

**只过第一层是不够的** —— 路通了不代表数据对。
很多坑（时间单位、容量口径、辅助通道列名）都是在第二、三层才暴露的。

---

# 阶段一：去要东西（越早越好，可以并行）

这个阶段全是"等别人"，所以要**第一天就发出去**。
等待期间可以做阶段二、三里不依赖这些东西的部分。

## 第 1 关：拿到 API 注册码

**做什么**：向新威（Neware）索取 API 模式注册码。

**为什么**：设备厂商给软件留了一个"允许外部程序来问数据"的功能，但这个功能**出厂是关着的**，
需要一串注册码才能打开。没有它，后面所有步骤都无从谈起 —— 这是唯一的"一票否决项"。

**过关标志**：手里拿到一串注册码。

**卡住查什么**：这是纯流程问题，只能催。同时把这几样一起要了，省得来回跑第二趟：

| 一起要的东西 | 为什么要 |
|---|---|
| API 调试小程序（TestAPI）**及其源码** | 小程序用来在写代码前先验证通讯通不通；**源码更重要** —— 能看出它连上后第一条发的是什么（协议里有个说不清的地方，见第 7 关） |
| 与现场版本对应的协议文档 | 我们手上的文档是 2023 年 9 月的版本，现场可能不一样 |
| `LogCode.csv` | 日志码对照表。没有它，"保护""异常"这类事件只看到一个数字，不知道是什么意思，报告里的异常归因就写不出来 |
| 《辅助通道参数类型.docx》 | 数据里那些 `V1` `T1` `Thk1` 列，没有这份文档就不知道哪个是温度、哪个是厚度 |

## 第 2 关：问清楚"客户端在哪台电脑上"

**做什么**：向设备负责人问三件事。

| 要问的 | 为什么要问（人话版） |
|---|---|
| 跑 BTS Client 的那台电脑，IP 是多少？ | 我们的程序要知道"去哪台电脑取数据" |
| 我们的程序打算跑在哪台电脑上？ | 决定用哪种连接方式，见下面 |
| 客户端软件的版本号是多少？（帮助 → 关于） | 版本太老就没有 TCP 功能，只能用管道 |

**为什么这两台机器是不是同一台这么重要**：
连接方式有两种，一种叫管道（只能在自己这台电脑上用），一种叫 TCP（可以跨电脑）。
**如果是两台不同的电脑，管道就彻底用不了，只能走 TCP。** 这会改变后面所有的配置。

**过关标志**：有三个明确答案。

**卡住查什么**：设备负责人可能不知道"IP 是多少"，教他这样做：
在这台电脑上按 `Win+R`，输入 `cmd`，在黑色窗口里输入 `ipconfig`，找"IPv4 地址"那一行。

## 第 3 关：确认"数据在谁手上"

**做什么**：确认测试数据是不是就存在跑 BTS Client 的这台电脑上。

**为什么**：协议里有一条限制 —— 取历史数据的命令**只能拿本机（127.0.0.1）的数据**。
第一次看到会觉得是障碍，其实不是：

```
BTS Client 这台电脑
  ├── 它自己身上的数据（127.0.0.1）→ 能给你
  └── 别的机器上的数据          → 给不了，它不代理别人的磁盘
```

但请注意：**这个"本机"是相对于 BTS Client 说的，不是相对于我们说的。**
所以哪怕我们的程序在另一台电脑上、走 TCP 连过去，
从 BTS Client 自己的视角看，数据依然在它的本机上 —— **完全没问题，这条路是通的。**

**过关标志**：确认数据在客户端本机上（正常情况下都在）。

# 阶段二：把客户端弄成"可用状态"

这一步是**在一台电脑上点鼠标**，不写代码。顺序不能乱。

## 第 4 关：装客户端并启动

**做什么**：安装 `BTS_Client_8.0.0_XXXX`（需要的话一并装服务器端），然后**用管理员权限启动**它。

**为什么必须管理员权限**：这不是软件故意刁难，是 Windows 内核的硬性规定。
简单说：以管理员身份运行的程序（比如客户端），会给自己创建的资源打个标签
"不允许权限更低的程序来写"。我们的程序要发命令给它，就必须有"写"的权限，
所以也得把自己提到同样的权限级别。**不用管理员，内核直接拒绝，报错"访问被拒绝"。**

**过关标志**：客户端界面打开，能看到设备列表和通道。

**卡住查什么**：右键客户端图标 → "以管理员身份运行"。这一步现场可能已经做好了。

## 第 5 关：激活 API 功能

**做什么**：
1. 客户端菜单栏 →【帮助】→【模式设置】
2. 在"激活码"框里填入第 1 关拿到的注册码
3. 点击【激活】
4. **重启客户端**（这步容易忘，不重启不生效）
5. 再打开模式设置，把鼠标**悬停在【已激活】上**，应该能看到包含 `API` 字样的注册模式

**为什么要重启**：软件启动时才读取激活状态，当场激活不会立即生效。

**过关标志**：悬停【已激活】能看到 API 字样。

**卡住查什么**：注册码是不是完整（别漏字符）；是不是忘了重启；是不是用错了机器的注册码（注册码可能和机器绑定）。

## 第 6 关：确认版本够新

**做什么**：客户端菜单栏 →【帮助】→【关于】，记下版本号。

**为什么**：TCP 连接方式需要 **2023 年 3 月 17 日之后**的版本 ——
那个日期之后新威才在客户端里加了"监听网络端口"的功能。
老版本根本没这个功能，用 TCP 连它只会得到"连接被拒绝"。

**过关标志**：版本号 ≥ 2023/3/17。

**卡住查什么**：版本太老就两种情况 —— 要么只用管道（前提是同机），
要么找新威升级客户端。

## 第 7 关：看内存够不够

**做什么**：确认这台电脑的内存占用**低于 90%**。任务管理器能看。

**为什么**：厂商文档明确说内存超过 90% 会导致**取到的数据不完整**。
原理是：程序之间传数据要靠内核里的一块缓冲区，系统内存紧张时缓冲区可能分不到足够空间，
数据就会被截断。另外客户端自己组装上千条数据的回应也需要大块内存。

**过关标志**：内存占用 < 90%。

**卡住查什么**：关掉不用的软件。这条看着土，但它是"数据缺行"最常见的非协议原因。

# 阶段三：验证（从官方工具到我们的工具）

**顺序非常重要**。先用官方工具，再用我们的工具。
原因见下面第 8 关的解释。

## 第 8 关：用官方 TestAPI 点一下 —— 这是分水岭

**做什么**：启动官方给的 TestAPI 小程序，让它连上客户端，
点【设备信息】按钮，再点【发送】。

**为什么这一步是整个流程的分水岭**：

通讯链路上有四个环节，任何一个断了都不通：

```
我们的代码  →  连接方式  →  客户端  →  测试柜
```

如果一上来就用我们自己的代码测，失败了，你**根本不知道是哪个环节的问题** ——
会陷入"到底是我代码写错了还是设备没开"的泥潭，可能耗掉好几天。

而 TestAPI 是**新威自己写的**，它肯定是好的。所以：

| TestAPI 的结果 | 说明什么 | 下一步 |
|---|---|---|
| **有正确返回** | 设备、客户端、连接方式、激活状态**全都是好的**。问题范围只剩"我们的代码" | 放心进入第 9 关 |
| **没有返回** | **问题不在代码**，在设备或客户端 | 按下面"卡住查什么"排查 |

这就是**控制变量法**：先换上一个你认为肯定没问题的零件，看还坏不坏。

**过关标志**：点【设备信息】后，输出框里出现一段包含 `<cmd>getdevinfo_resp</cmd>` 的文字。

**卡住查什么**（按顺序）：

1. 客户端是不是开着？
2. API 是不是激活了？**改完激活重启过没有？**
3. 用管道方式的话，TestAPI 是不是以**管理员权限**启动的？
4. 用 TCP 方式的话，**502 端口是不是被别的程序占用了**？
5. TCP 方式的话，客户端版本够不够新（第 6 关）？
6. 防火墙有没有拦？
7. 命令内容跟协议文档**逐字对得上吗**（大小写！）

## 第 9 关：拿到通道清单和电池条码

**做什么**：用我们的工具自动列出所有通道。

```bash
cd neware_comms
python neware_client.py --transport tcp --host <客户端IP> info
```

**为什么**：要操作某一颗具体的电池，必须说清地址。地址是四段数字，
像快递地址一样逐级缩小范围：

| 字段 | 像什么 | 含义 |
|---|---|---|
| `devtype` | 哪个小区 | 设备型号（22=BTS80、25=BTS83……） |
| `devid` | 哪一栋 | 设备编号 |
| `subdevid` | 哪一层 | 机箱编号 |
| `chlid` | 哪个房间 | 通道号，**一个通道接一颗电池** |

**不要手工猜这些数字** —— 上面那条命令会自动列出来。

同时还要问设备负责人拿到一张**"通道 ↔ 电池条码"的对应表**。
**这张表是整个项目"按同一测试对象关联"的落点**，
也是后面数据库里"哪颗电池、哪次实验"的入口。没有它，数据就是一堆没有归属的数字。

**过关标志**：清单里有通道；手上有条码对应表。

## 第 10 关：跑全面体检

**做什么**：

```bash
python probe.py --transport tcp --host <客户端IP>
```

**为什么**：这一条命令会把协议里 8 个环节挨个走一遍，
而且**直接从数据里反推那几个容易踩的坑**，不靠假设。它会告诉你：

| 检查项 | 在查什么 | 为什么必须查 |
|---|---|---|
| 连接 | 路通不通 | 第一层验收 |
| 设备信息 | 有哪些通道 | 确定要操作谁 |
| 通道状态 | 现在是在测试、停止还是保护 | 状态机是 8 种，得对得上 |
| 实时数据 | 现在读数多少 | 确认能读到"此刻"的值 |
| 历史数据 | 能把明细拉下来吗 | 第二层验收 |
| 工步层数据 | 每一步的汇总，**含内阻 DCIR** | 算 SOH 最省事的数据源 |
| 上传完整度 | 数据都传完了吗 | **没传完就取数，会缺数据** |
| 日志 | 有没有异常事件 | 需要 LogCode.csv 才能读懂 |

**过关标志**：8 项基本都 PASS，并且最后出现"SOH 数据可行性预览"。

## 第 11 关：看 SOH 预览能不能出来 —— 这是终点的标志

体检脚本最后会直接算一遍 SOH 并打印：

```
--- SOH 数据可行性预览 ---
  循环数              100（1 → 100）
  首圈放电容量        3.2134 Ah
  末圈放电容量        2.8765 Ah
  容量保持率          89.52 %
  库仑效率 首/末      99.81 % / 99.64 %
  DCIR 首/末 (mΩ)     12.3 / 18.7
```

**为什么这一节最重要**：它意味着**"数据读取 → 指标计算"这条链路已经完全验证了**。
后面要做的只剩"按模板排版成报告"，那是纯体力活，没有技术风险了。

**过关标志**：这些数字都出来了，而且跟 BTSDA 官方软件导出的结果对得上。

**卡住查什么**：

| 现象 | 可能原因 |
|---|---|
| 说"找不到有效的放电容量" | 工步类型的定义和预期不一样，需要现场核对每种类型是什么意思 |
| 时间相关的数字离谱 | `testtime` 单位搞错了（协议里有的地方是毫秒、有的是秒） |
| 内阻是空的 | 测试工步里没开 DCIR 计算，需要在工步设置里打开 |

# 附带一张概念速查表

每个概念一句话，方便随时回查。

| 概念 | 一句话解释 |
|---|---|
| **API** | 让程序（而不是人）去调用软件功能。这里是"让程序问客户端要数据"的功能 |
| **协议** | 两个程序对话的规则手册：能说什么、怎么说、对方怎么答 |
| **注册码** | 打开 API 功能的钥匙。出厂是关着的 |
| **BTS Client** | 跑在电脑上的客户端软件，数据都存在它这里 |
| **TestAPI** | 新威官方的调试小工具，用来在写代码前先验证通讯通不通 |
| **BTSDA** | 新威官方的数据分析软件。用它导出结果作为我们解析的对照基准 |
| **管道** | 同一台电脑上两个程序之间的通道。**不能跨电脑，需要管理员权限** |
| **TCP** | 通过网络跟另一台电脑上的程序通讯。需要 IP 地址 + 端口号 |
| **IP 地址** | 电脑在网络上的地址，比如 `192.168.1.20` |
| **端口** | 一台电脑上"哪个程序在接电话"的编号。客户端固定用 **502** |
| **127.0.0.1** | "本机"的意思，指自己这台电脑 |
| **管理员权限** | Windows 的最高权限。管道方式必须用它 |
| **通道地址** | 四段数字 `devtype-devid-subdevid-chlid`，四级门牌号，定位到具体一颗电池 |
| **条码（barcode）** | 电池的身份证号。把数据和"哪颗电池、哪次实验"关联起来的关键 |
| **工步** | 测试程序里的一步，如"恒流充电到 4.2V"，共 17 种类型 |
| **循环** | 一次完整的"充满 + 放完" |
| **实时数据** | "此刻"的读数，用来做进度监控 |
| **历史明细** | 一条条的历史记录，算指标的主要数据源 |
| **工步层数据** | 每个工步一行的汇总，**自带内阻 DCIR**，算 SOH 最省事 |
| **辅助通道** | 主通道之外的额外测量，如温度、辅助电压。列名随硬件变化 |
| **DCIR** | 直流内阻，单位毫欧。电池老化的关键指标 |
| **SOH** | 电池健康度 = 当前容量 ÷ 初始容量 |
| **容量保持率** | 第 N 圈的放电容量 ÷ 第 1 圈的放电容量。SOH 的核心 |
| **库仑效率** | 放电容量 ÷ 充电容量。差得多说明有副反应在消耗电 |
| **LogCode.csv** | 日志码对照表。没有它，异常事件只看到一个数字 |
| **NDA / NDAX** | 新威的数据文件格式。属于"离线文件路线" |
| **TestAPI 源码** | 比工具本身更有价值 —— 能看出协议文档没写清的地方到底怎么发 |

# 调通之后，离交付还差什么

调通只解决了"取数据"。要交的那个 Demo 还需要：

```
① 取数据     ← 调通通讯就完成了这一步
② 算指标     ← 体检脚本的 SOH 预览已经验证了算法可行
③ 出报告     ← 需要先拿到报告模板（关键路径，要尽早催）
④ 打包成 Agent 能调的服务  ← 让大模型通过接口去取数、算数、写报告
```

其中**第 ③ 步的报告模板是关键路径**：模板决定了要取哪些字段、算哪些指标，
模板不定，第 ② 步的口径就定不下来，会反复返工。

建议在阶段一（等注册码的那几天）就同时去催模板，别等到通讯通了才想起来。
